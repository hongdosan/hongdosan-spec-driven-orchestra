# 🎤 AI 진입 - SDD 셋업 & 컨텍스트 평가

> **Claude Code가 이 파일을 읽으면 컨텍스트를 평가하고, 강제 게이트를 설치한 뒤, SDD(AI-EXECUTION.ko.md)를 실행합니다.**
> 모드는 없습니다. 흐름은 항상 같으며, 평가는 강제 레벨과 0단계 조사 필요 여부만 정합니다.

---

## 🎯 미션

목적은 **프로젝트 컨텍스트를 평가**해 SDD를 설정하는 것입니다 — 모드를 고르는 게 아닙니다. 두 가지를 정합니다:

```
1. 강제 레벨:
   [ ] standard : 기본 (R1–R5; R3/R4는 기록 남기고 1회 우회 가능)
   [ ] strict   : 운영 시그널 감지 시 자동 (R1–R6; 우회 불가)

2. 흐름에 0단계 조사가 필요한가?
   [ ] yes : 기존 코드 있음 → 바꾸기 전에 이해 (00-survey, 05b-regression 추가)
   [ ] no  : 신규 → 보존할 게 없음
```

같은 SDD 흐름이 모든 경우에 실행됩니다. 컨텍스트는 *게이트 엄격도*만 바꾸며, *SDD가 하는 일*은 바꾸지 않습니다.

## 2. 운영 컨텍스트 처리 (strict 강제, 차단 아님)

Q1에서 운영 시그널이 드러나면 **차단하지 않습니다**. 대신 `strict`로 설정하고 보고:

```markdown
## 🔒 운영 컨텍스트 감지됨 → strict 강제

운영 프로젝트이므로 SDD가 **strict** 강제로 적용됩니다 (차단 아님).

### 여기서 "strict"의 의미
- R3(테스트 통과)와 R4(회귀로 동작 보존)가 **필수**
- 우회 불가: `SDD_OVERRIDE` 탈출구 비활성화
- 기존 코드 변경 전 0단계 조사 실행
- pre-commit과 CI 게이트가 테스트/회귀 건너뛰는 것을 거부

### 왜 차단하지 않나?
안전한 AI 보조 변경이 가장 중요한 곳이 바로 운영입니다. 거부하는 대신 SDD는
기준을 높여 게이트를 타협 불가로 만듭니다. 흐름은 다른 곳과 동일하며 — 엄격도만
올라갑니다.

### 권장 접근 (여전히 본인 선택)
1. 운영 영향 없는 feature branch에서 시작
2. 새 기능 1개부터 SDD 적용; 게이트가 스스로 가치를 증명하게
3. 팀 합의 후 확대

진행: 강제 레벨 = **strict**, 0단계 조사 = **켬**.
```

**처리**:
- 운영 시그널 → `ENFORCEMENT_LEVEL=strict`, 일반 흐름 진행
- 운영 코드베이스를 보호하는 것은 거부가 아니라 게이트

## 3. 컨텍스트 기반 셋업 가이드

고를 모드는 없습니다. 컨텍스트 신호를 읽고 두 가지를 설정합니다: 강제 레벨과 0단계 조사 실행 여부. SDD 흐름 자체는 모든 경우에 동일합니다.

### 신호 → 강제 레벨

| 신호 | 레벨 | 효과 |
|---|---|---|
| 운영 시그널 (배포 설정, `.env.production`, `Dockerfile.prod` 등) | **strict** | R3/R4 필수, 우회 불가 (R6) |
| 위 항목 없음 | **standard** | R1–R5; R3/R4는 기록 남기고 1회 우회 가능 |

### 신호 → 0단계 조사

| 신호 | 조사 | 추가 |
|---|---|---|
| 기존 코드 있음 (코드 파일 > 약 10, 또는 의미 있는 git 이력) | **켬** | `00-survey.md`, `05b-regression.md` (R4) |
| 신규 (코드 거의 없음, 이력 없음) | **끔** | 없음 — 흐름이 Specify부터 시작 |

### 항상 동일

컨텍스트와 무관하게:
- 7단계 SDD 흐름이 진입점 (작업 규모로 full/mini/none 조절)
- 강제 게이트 설치 (`pre-implement`, `pre-commit`, `post-task`, CI)
- `SPEC.yml`과 `sdd/CONSTITUTION.md`가 단일 출처
- 첫 기능은 `F001-[기능]` (모드별 특수 `F000-*` 부트스트랩 없음)

### 단계(Tier) (컨텍스트와 독립)

모드가 아니라 프로젝트 규모와 작업 형태로 시작 단계를 추천:
- **Tier 1**: SDD + Karpathy + grill-me
- **Tier 2**: + Handoff
- **Tier 3**: + Verification Design + Harness (대형/팀 작업; Harness 선택·실험적)

- 자연스러운 대화 흐름

#### 2. 추천 답변은 근거 명시
- "추천: A" 만 적지 말고
- "추천: A (이유: 코드 파일 8개로 신규로 보임)"

#### 3. 사용자 답변 존중
- AI 추측과 달라도 사용자 답변 우선
- 단, 명백히 모순되면 한 번 더 확인:
  "코드가 50개 있는데 신규라고 하시는 게 맞나요?"

#### 4. 운영 프로젝트 감지 강화
- Q1 답변이 애매하면 (예: "글쎄요") 추가 질문
- 운영 시그널이 있는데 사용자가 "아니오"라면 명시적 재확인:
  "Dockerfile.prod가 있는데 운영 아닌가요? strict 강제가 설정됩니다."

### 🚫 AI가 하지 말 것

- 평가 건너뛰고 바로 실행 X
- 사용자 답변 무시 X
- 강제 레벨을 말없이 바꾸기 X
- 운영을 strict 신호가 아닌 차단 사유로 취급 X

## 7. 평가 시 자주 발생하는 상황 가이드

### 상황 1: 사용자가 "잘 모르겠어요"

```
대응:
1. AI 추천 답변을 기본값으로 채택
2. INTERVIEW-RESULT.md에 "사용자 미결정, AI 추천 채택" 기록
3. 다음 질문 진행
```

### 상황 2: 답변이 서로 모순

```
예: Q2=신규, Q4=archive 필요
대응:
1. 한 번 더 확인
2. 사용자가 의도적이라면 그대로 진행
3. 실수면 수정
```

### 상황 3: 운영 시그널 강한데 사용자 부정

```
예: Dockerfile.prod 존재, .env.production 있음
대응:
1. 명시적 재확인:
   "production 관련 파일들이 있는데, 정말 운영 환경이 아닌가요?
    혹시 운영 예정인 프로젝트인가요?"
2. 그래도 "운영 아님" 답변이면 진행
3. INTERVIEW-RESULT.md에 "운영 시그널 발견, 사용자 부정함" 기록
```

### 상황 4: 사용자가 평가 중간에 마음 바꿈

```
예: Q5 답변 후 Q2 답변 수정 요청
대응:
1. 흔쾌히 수정
2. INTERVIEW-RESULT.md에 변경 이력 기록
3. 영향 받는 질문 다시 검토
```

### 상황 5: 패키지 부적합한 프로젝트

```
예: 운영 프로젝트로 판명
또는: 통합 자체가 이득이 없어 보임 (코드 5줄짜리)
대응:
1. 솔직히 말함
2. 적합하지 않은 이유 설명
3. 대안 제시
4. 진행 거부
```
