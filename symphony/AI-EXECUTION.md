# 🛠️ AI Execution Guide — Single SDD Flow

> **This file runs after AI-INTERVIEW.md completes.** There is one flow for every project; context (existing code, production signals) only adds steps and raises enforcement strictness.

> [!NOTE]
> Respect the **tier** chosen in assessment. Tier 1 = SDD + Karpathy + grill-me; Tier 2 adds Handoff; Tier 3 adds Verification Design + 🎸 Harness. Generate only what the tier calls for — don't impose everything on a Tier 1 project. 🎸 Harness is an external plugin, brought in only when a task needs an agent team.

---

## 📌 Entry Point

From the assessment, two settings drive execution:

- **Enforcement level**: `standard` or `strict` (strict = production; gates non-bypassable)
- **Step 0 survey**: on (existing code) or off (greenfield)

The flow itself is identical in all cases. Sections below:
- [Common Principles](#-common-principles) → always apply
- [Common Assets](#-common-assets) → always generated
- [Existing-Code Skills](#-existing-code-skills-survey--migration) → used only when existing code is present
- Appendices → the standard templates

---

## 🌐 Common Principles

### Autonomous Execution
- Proceed without user confirmation (already approved in assessment)
- Unlimited time/tokens
- Log every decision in DECISION-LOG.md

### Safety
- Never touch global settings (`~/.claude/`)
- Never delete the contents of archive/
- Keep everything Git-trackable

### Reporting
- Brief report at the end of each Phase
- Auto-advance to the next Phase
- Comprehensive report on completion

## 🔁 Execution Flow (single, universal)

There is one flow. It does not branch by mode. Two settings from assessment shape it:
**enforcement level** (standard/strict) and **Step 0 survey** (on/off). Everything below
runs the same way for new, legacy, and production projects.

### Phase 1: Install the enforcement layer (always)

```bash
# Constitution (rules R1–R7 the gates read)
mkdir -p sdd && cp enforcement/sdd/CONSTITUTION.md sdd/CONSTITUTION.md

# Local hooks
mkdir -p .claude/hooks
cp enforcement/hooks/pre-implement.sh .claude/hooks/
cp enforcement/hooks/post-task.sh    .claude/hooks/
cp enforcement/hooks/pre-commit.sh   .git/hooks/pre-commit
chmod +x .claude/hooks/*.sh .git/hooks/pre-commit

# CI gate + sync-check (R7)
mkdir -p .github/workflows
cp enforcement/github-workflows/sdd-gate.yml .github/workflows/

# Set the verification command the gates use
export SDD_TEST_CMD="[npm test | pytest -q | go test ./... | cargo test]"

# If strict (production signals): set the level so R3/R4 become non-bypassable
# export ENFORCEMENT_LEVEL=strict
```

> This phase is what makes the package "enforced, not advised." It runs first so that
> every later step is already under the gates.

### Phase 2: Create common assets (always)

```bash
# The 5 skills SDD calls
mkdir -p .claude/skills/{grill-me,sdd-conductor,karpathy-enforcer,harness-builder,handoff-writer}
mkdir -p sdd/{templates,features}
# (🎸 Harness is an external plugin — installed separately only when a task needs an agent team)
```

Write `sdd/CONSTITUTION.md` reflecting the project identity, the Karpathy 4 principles,
the SDD 7 steps, and the enforcement level. The constitution is the same document in all
contexts; only the "current stage" line and the enforcement level differ.

### Phase 3: Create the standard templates

- Always: the 7 standard templates (`01`~`07`) — see Appendix A.
- **If Step 0 survey is on** (existing code): also create `00-survey.md` and
  `05b-regression.md` (see "Existing-Code Skills" below).

### Phase 4: Step 0 — Survey (only if existing code is present)

Skip entirely on greenfield. If existing code is present, understand it before changing it:

```bash
# Back up existing assets first (never modified, only referenced)
mkdir -p archive/
[copy existing code/docs/config → archive/legacy/...]
# Write archive/README.md (mapping + rollback method)
```

Then run the survey (see Existing-Code Skills) and record behaviors to preserve
(B1, B2, ...) in `00-survey.md`. These feed `05b-regression.md` (R4).

### Phase 5: First SDD cycle (F001-[feature])

Run the standard flow for the first real feature. There is no mode-specific `F000-*`
bootstrap; the first feature is simply `F001`:

```
sdd/features/F001-[feature]/
├── 00-survey.md          # only if existing code present
├── 01-spec.md            # What & Why
├── 02-clarify.md         # grill-me
├── 03-plan.md            # How (tech, architecture)
├── 04-tasks.md           # breakdown (+ optional 🎸 Harness agent team)
├── 05-harness.md         # verification (5 categories)
├── 05b-regression.md     # only if existing code present (preserve B1, B2, ...)
├── 06-implementation-notes.md
└── 07-handoff.md
```

⛔ Gates active throughout: no implement without `01-spec.md` + `03-plan.md` (R1/R2);
no commit without passing verification (R3) and, if existing code is touched, regression (R4).

### Phase 6: Write CLAUDE.md

```markdown
# CLAUDE.md - AI Coding Guide

## One-Line Summary
AI coding conducted by SDD (Spec-Driven Development), with skills it calls and
enforcement gates that make the flow non-optional.

## First action when starting work
| Task type | First action |
|---|---|
| New feature | sdd-conductor → new F[ID] |
| Touching existing code | run Step 0 survey first |
| Small decision | log in DECISION-LOG.md |

## Anti-Patterns
- ❌ Coding before spec/plan (the gate will block it)
- ❌ Committing without passing tests (the gate will block it)
- ❌ Touching existing behavior without regression (the gate will block it)
- ❌ Giant abstractions on day one (Karpathy: Simplicity First)
```

### Phase 7: Verification + final report

Run the Day 0 checks from INTEGRATION-CHECKLIST.md and report what was generated,
the enforcement level set, and whether the gates are active.

## 🧱 Existing-Code Skills (Survey + Migration)

These are used **only when existing code is present** — they are not a mode, just the
skills SDD calls during Step 0 and during Implement when behavior is being replaced. On
greenfield projects they never appear.

### Code survey skill (Step 0)

`.claude/skills/code-archaeologist/SKILL.md`:

```markdown
---
name: code-archaeologist
description: |
  Analyzes existing code to identify behavior/intent/dependencies.
  Activates at Step 0 when existing code is present.
  Keywords: "survey", "analyze existing code", "reverse-engineer"
---

# Code Survey

You survey existing code. Excavate the intent buried in it.

## Core Responsibilities
1. Behavior mapping — what the code does (input → processing → output, dependencies)
2. Intent inference — why it was written this way, what it solved
3. Trap identification — invisible side effects, implicit assumptions, breakage risks

## Output
Write `sdd/features/F[ID]/00-survey.md` (see template below).
```

### Migration skill (Implement, when replacing behavior)

`.claude/skills/migration-strategist/SKILL.md`:

```markdown
---
name: migration-strategist
description: |
  Plans gradual, safe transition when replacing existing behavior.
  Activates during Implement when existing code is being changed.
  Keywords: "migration", "gradual transition", "strangler fig"
---

# Migration Strategy

You plan gradual transition.

## Strategy Patterns
1. Strangler Fig — gradually replace old with new, keep the external interface
2. Feature Flag — toggle new code on/off, instant rollback, gradual rollout
3. Branch by Abstraction — introduce an abstraction layer, swap implementations

## Output
Specify the chosen migration strategy in `06-implementation-notes.md`.
```
